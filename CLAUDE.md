# CLAUDE.md — cykel-service-v0

Baseline for every Claude session on this project. If you want to change a rule, change it here — don't override it locally.

Stack facts, commands, path ownership and known deviations: see `docs/STACK.md`.

## Project context

- **What:** A service management app for small bike workshops — tracks customers, their bikes and repair jobs. A lightweight alternative to a full POS/ERP system.
- **Platforms:** iOS, Android and Web from one Expo codebase.
- **UI language:** Danish (*Kunder*, *Reperationer*, *Opret kunde* …).
- **Status:** Early-stage. Interfaces and the Supabase schema are still in flux.

## Tech stack

## Architecture

```
.claude/skills/             Shared Claude skills (create-pr)
app/                        Expo Router routes
  (tabs)/                     Tabs: Forside, Kunder, Reperationer
    customers/[id]/             Customer detail + nested bike detail ([bikeId].tsx)
    repairs/                    Repair list
  create*Modal.tsx            Modal screens for create flows
components/
  ui/                         Domain components/forms (createCustomerForm, RepairLinesSection …)
  ui/stock components/        Generic RN Reusables primitives (button, input, dialog …)
crud/                       Supabase data access, one file per table
store/                      Zustand stores, one per resource
types/                      Domain types: Customer, Bike, Repair, RepairItem
utils/supabase.ts           Supabase client (SecureStore on native, localStorage on web)
lib/                        theme + utils (cn helper)
```

Data flow — keep it one-directional:

```
Screen / component  ──▶  store (Zustand)  ──▶  crud/*.ts  ──▶  Supabase
        └────────────────────────────────────▶  crud/*.ts  (for create/update/delete)
```

Rules:

- **Only `crud/` talks to Supabase.** Screens, components and stores never call `supabase.from(...)` directly.
- **`crud/` maps between DB rows and domain types.** DB columns are `snake_case`; types in `types/` are `camelCase`. Mapping happens in `crud/` and nowhere else.
- **Stores hold client state** (lists, selected item, `isLoading`, `error`) and call `crud/` for fetching. After a mutation, update the store so the UI reflects it without a refetch.
- **Domain types live in `types/`** — don't redeclare `Customer`, `Bike`, etc. inline. Derive variants with `Omit`/`Pick` (e.g. `Omit<Customer, 'id'>`).
- **Stock components** (`components/ui/stock components/`) are generated by React Native Reusables. Prefer adding via `npx react-native-reusables/cli@latest add <name>` over hand-writing; avoid editing them for feature-specific needs — wrap them instead.
- **Focus on the web version** unless told otherwise. Build, test and verify changes against web (`npm run web`); don't spend effort on iOS/Android-specific behaviour unasked.
- **Platform-specific files** use Expo's suffixes (`index.web.tsx`, `createRepairModal.ios.tsx`). When a `.web.tsx` variant exists, that is the file to change. Mention it if a native variant now differs, but don't update it unless asked.
- Use the `@/` path alias for imports.

## Principles

- **Single responsibility:** a crud function fetches/writes; a store manages state; a component renders. Don't mix.
- **DRY:** one source of truth for types, row↔type mappings, and Supabase table/column names. Duplicate once if needed; extract on the third occurrence. DRY is about duplicated *knowledge*, not code that merely looks similar.
- **Reusable UI** goes into `components/ui/`.

## Coding conventions

- Follow `.prettierrc`: 2-space indent, single quotes, print width 100, trailing commas (es5).
- Naming: `PascalCase` for components and types, `camelCase` for functions/variables, stores as `use<Resource>Store`, crud functions as `get/create/update/delete<Resource>`.
- `async`/`await` for all I/O.
- Error handling in `crud/`: check `error` from Supabase and **throw** it, so the caller (store or form) can handle it. Don't swallow errors with `console.log`/`return error`.
- Styling with Nativewind `className`; use `cn()` from `lib/utils` for conditional classes.
- Code and identifiers in **English**. User-facing UI text in **Danish**.
- No `any` — keep strict typing.

## Security

- Supabase URL/anon key come from `.env` (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_KEY`). Never hard-code keys and never put a service-role key in the app — everything `EXPO_PUBLIC_*` ships to the client.
- Data access must be protected by Supabase Row Level Security, not by client-side checks.

## Testing

- No test setup exists yet. Ask before adding a test framework.
- Place tests that you write yourself in a folder `Test/Claude`.

## How Claude should work in this repo

- Prefer minimal, targeted changes that follow existing patterns over large rewrites.
- Always make sure the local branch is up to date with remote before adding code; ask before changes are overwritten.
- Never git add, commit or push without explicit authorisation. Permission given once in a conversation does not extend to anything else.
- Create pull requests only via `/create-pr`, and only when asked. PRs target `main`.
- Before adding a new file/function, check whether an existing one already covers it or should be extended.
- Ask before: adding packages, changing the Supabase schema, changing auth/RLS, or changing this file.
- Keep explanations short and concrete.
- Keep code comments short and precise, and as much as possible place them above the function rather than inside it.
